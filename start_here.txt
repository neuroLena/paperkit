# PaperKit: start here

To write a paper you need Part A only. It takes about ten minutes.

`publish.sh` is a development tool. It commits the code and uploads it to GitHub.
You do not need it, a GitHub account, SSH keys or a token to write a paper.
All of that is in Part B, for when you change PaperKit's code and want it on GitHub.

What to do once PaperKit runs (inputs, steps and their order) is in
`sci_paper_writing_agent/README.md`.


# Part A. Set up and start

## 1. Run setup.sh first

Everything starts with this one command, in the `paperkit` folder:

```bash
cd paperkit
bash setup.sh
```

You need a Mac or Linux terminal and an internet connection.

What it does, in this order:

- Installs `uv` and Python 3.11 if they are missing.
- Creates the project folder `sci_paper_writing_agent/`.
- Creates `.env` (your keys, readable only by you), `.env.example` and `.gitignore` next to `setup.sh`.
- Creates the Python environment `.venv/` next to `setup.sh` and installs the packages.
- Runs the tests and prints the checklist of inputs. A new project fails that checklist: that is expected.
- Makes a first local commit. Nothing is uploaded. If Git does not know your name yet, it says so and carries on (see B1).

It is safe to run again. Files that exist are not overwritten.

Git must be installed for the commit step. If it is not, or you do not want a repository:

```bash
NO_GIT=1 bash setup.sh
```

The folders after setup:

```text
paperkit/
  setup.sh  scaffold.py  publish.sh  start_here.txt
  .env  .env.example  .gitignore  .venv/
  sci_paper_writing_agent/      the project: inputs, drafts, code, README.md
```

## 2. Put your keys in .env

The one `.env` file is in the `paperkit` folder, next to `setup.sh`. Open it:

```bash
nano .env
```

Fill in what you use:

```dotenv
# Required to call a model: one of these two keys
NVIDIA_API_KEY=YOUR_NVIDIA_API_KEY
ANTHROPIC_API_KEY=

# Which provider and model to use (IDs change: copy the ID from the model's page on build.nvidia.com)
PAPERKIT_PROVIDER=nvidia
PAPERKIT_MODEL=z-ai/glm-5.3

# Recommended with the free NVIDIA models: think less, and allow a long answer
PAPERKIT_REASONING=low
PAPERKIT_MAX_TOKENS=16000

# Optional: only for the literature search (free key at semanticscholar.org/product/api)
SEMANTIC_SCHOLAR_API_KEY=
```

In nano, save with Ctrl+O then Enter, and exit with Ctrl+X.

You do not have to load this file into the terminal: `paperkit` reads it by itself.
Instead of editing it by hand, you can also let `paperkit start`, menu 9, save the provider, the model and the key.

## 3. Start PaperKit

```bash
source .venv/bin/activate
paperkit start
```

`paperkit start` shows the checklist of inputs, helps you fill in what is missing, and then offers every step from a menu.

To check that the model answers:

```bash
paperkit ping
```

Now open `sci_paper_writing_agent/README.md`. It lists the steps in order and says which inputs and steps are required and which are optional.

## 4. Every later session

```bash
cd paperkit
source .venv/bin/activate
paperkit start
```

## 5. Updating to a newer scaffold.py

Replace `scaffold.py` in the `paperkit` folder with the new one, then:

```bash
UPDATE_CODE=1 bash setup.sh
```

This refreshes the code, the tests and the README in the project. Your inputs, `paper.yaml`, drafts, claim tables and rules are never overwritten.
If a new version adds a section to the default `paper.yaml` (for example the Introduction), add it to your own `paper.yaml` by hand.

To run the tests yourself:

```bash
cd sci_paper_writing_agent
python -m pytest -q
```


# Part B. Development only: Git, GitHub and publish.sh

Skip this part unless you change PaperKit's code and want to keep it on GitHub.

What `publish.sh` uploads: the scripts, the code, the configuration, the rules, the wiki pages and the reference library.
What it never uploads (the `.gitignore` keeps them out): `.env`, `.venv/`, `inputs/`, `drafts/`, `state/`, `facts/`, `build/`, `.papers/`, `.writing_guides/` and `.cache/`.
So your manuscript text is not backed up by it: keep your own copy of `inputs/` and `drafts/`.

## B1. Tell Git who you are (first time only)

```bash
git --version
git config --global user.name "YOUR_NAME"
git config --global user.email "YOUR_GITHUB_EMAIL"
```

These settings name the author of commits. They do not sign you in to GitHub.
Without them, the commit step of `setup.sh` and `publish.sh` stops with a message that asks for them.

## B2. Set up SSH for GitHub (first time only)

Check whether you already have a key:

```bash
ls -la ~/.ssh
```

If `id_ed25519` and `id_ed25519.pub` are not there, create a key:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -C "$(git config --global user.email)"
```

Press Enter to accept the default location. A passphrase is optional.

Start the agent and add the key (macOS):

```bash
eval "$(ssh-agent -s)"
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
```

Open the SSH configuration file:

```bash
touch ~/.ssh/config
chmod 600 ~/.ssh/config
nano ~/.ssh/config
```

Add this, if there is no GitHub entry yet:

```text
Host github.com
    HostName github.com
    User git
    AddKeysToAgent yes
    UseKeychain yes
    IdentityFile ~/.ssh/id_ed25519
```

Copy the public key and add it at https://github.com/settings/keys (New SSH key):

```bash
pbcopy < ~/.ssh/id_ed25519.pub
```

Test it:

```bash
ssh -T git@github.com
```

On the first connection, compare the fingerprint it shows with the ones GitHub publishes before you accept it.
The expected answer is:

```text
Hi YOUR_USERNAME! You've successfully authenticated, but GitHub does not provide shell access.
```

## B3. A GitHub token (only to create the repository)

`publish.sh` needs a token once, to create the repository on GitHub. Later pushes use SSH.
You can skip the token if the GitHub CLI (`gh`) is installed and signed in, or if you create an empty repository yourself and add it as the remote:

```bash
git remote add origin git@github.com:YOUR_USERNAME/REPOSITORY_NAME.git
```

To make a token: open https://github.com/settings/tokens, choose Tokens (classic), Generate new token (classic), with the scope `repo` and an expiry of 30 or 90 days.

Put it in `.env`, with your user name:

```dotenv
GITHUB_USER=YOUR_GITHUB_USERNAME
GITHUB_TOKEN=YOUR_GITHUB_TOKEN
VISIBILITY=private
```

## B4. Publish

From the `paperkit` folder:

```bash
bash publish.sh "Describe the changes"
```

The script, in this order:

- Stops if a folder inside has a Git repository of its own.
- Makes this folder a Git repository, if it is not one yet.
- Stops if `.env` is not ignored.
- Stops if a file that would be committed looks like it holds an API key.
- Commits everything that is not ignored.
- On the first push, asks for the repository name and whether it is private or public, creates it on GitHub, and sets the SSH remote.
- Pushes.

To name the repository without being asked:

```bash
REPO_NAME=my-paperkit VISIBILITY=private bash publish.sh "Initial commit"
```

To commit without uploading:

```bash
LOCAL_ONLY=1 bash publish.sh "Local changes"
```

Other commands you may need:

```bash
git remote -v     # where it pushes to
git pull          # fetch changes from GitHub
```

## B5. What must never be uploaded

- `.env` and any other file that holds a key.
- Private SSH keys. Only the public key, the file ending in `.pub`, goes into GitHub's settings.
- `.venv/`, `.cache/`, `.papers/` and `.writing_guides/`.
- Confidential research data, and model logs that contain it (`state/log/`).

The `.gitignore` that `setup.sh` creates already covers these folders, and `publish.sh` checks `.env` and scans for keys before every commit.
